1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) defines the functional and non-functional requirements for an AI-first operations platform for a textile wholesaler and manufacturer in Surat. It is intended for the client (owner/stakeholders), the engineering team building the system, and any future maintainers. It is the authoritative reference against which the system will be designed, built, and accepted.
1.2 Scope
The system replaces manual data entry with AI-based capture and provides automated reporting, a conversational query interface, and camera-based worker-efficiency monitoring. It covers three operational problems: stock inventory (incoming/outgoing), job-card meter updates with folding-shortage calculation, and worker efficiency (allotted vs done, with flagging).
In scope: photo-based capture of meters/lots/challans; a Postgres system of record; an AI brain for daily reports and natural-language queries over firm history; CCTV-based activity monitoring fused with job-card output; web and mobile (PWA) interfaces with role-based access.
Out of scope (v1): accounting/billing/GST software replacement; direct machine/PLC control; automated payroll actions; e-commerce or customer-facing portals.

2. Overall Description
2.1 Product Perspective
The platform is a new, self-contained system. Three input channels (worker photo capture, CCTV streams, and admin chat) feed a single backend and Postgres database that acts as the system of record. AI services for vision, the reasoning brain, and video analytics run as independent modules behind the backend. A web/PWA presentation layer serves owner, supervisors, and workers according to role.
2.2 Product Functions (summary)
Capture incoming and outgoing stock by photographing challans/lot tags; AI extracts lot, quality, and meters.
Capture job-card folding meters; AI records meters-out and computes shortage automatically.
Hold low-confidence readings for one-tap human confirmation before committing.
Generate an automated end-of-day report without manual assembly.
Answer natural-language questions over the full firm history via a chat assistant.
Monitor worker activity via CCTV, fuse it with job-card output, and flag low efficiency.
Enforce role-based access for owner, supervisor, and worker.

2.4 Operating Environment
Capture clients: modern mobile/tablet browsers (PWA), Android-first.
Admin/supervisor: desktop and tablet browsers.
Backend: Linux container host; Node.js/TypeScript; Postgres (Supabase).
CCTV analytics: on-site edge GPU device (recommended) on the factory LAN.
Connectivity: intermittent internet tolerated; capture queues locally and syncs.
2.5 Design and Implementation Constraints
Database is the single source of truth; AI must never assert figures not backed by a query.
Chat queries run under a read-only database role; no AI-initiated writes.
Vision provider must be abstracted so a hybrid OCR path can be added without rework.
Worker video should remain on-premises where feasible (privacy/labour considerations).
UI text and capture flows must accommodate English, Hindi, and Gujarati numerals.
2.6 Assumptions and Dependencies
Scale: ~18 cameras and ~300–500 capture events/day (medium).
Cloud multimodal LLM (Claude) availability for vision and the brain.
Adequate camera placement and lighting at each workstation.
Client agrees a worker-monitoring policy (coaching vs punitive) before go-live.
3. External Interface Requirements
3.1 User Interfaces
Worker capture (PWA): camera-first screen, large capture button, instant preview of AI reading, one-tap confirm/correct, offline queue indicator.
Supervisor console: pending-confirmation queue, allotment management, section dashboards, flags.
Owner dashboard: live stock/shortage/efficiency tiles, daily report viewer, chat panel.
Accessibility/locale: multilingual labels; high-contrast, touch-friendly controls for floor use.
3.2 Hardware Interfaces
Mobile/tablet cameras for capture.
IP/CCTV cameras (RTSP) feeding the edge analytics device.
Edge GPU device interfacing with the backend over the LAN/API.

5.2 Reliability & Availability
NFR-R1: Application availability target 99% during working hours.
NFR-R2: No capture data loss; offline submissions queued and synced (supports FR-3.6).
NFR-R3: Edge CCTV continues functioning during internet outages.
NFR-R4: Automated daily backups of the database with point-in-time recovery.
5.3 Security & Privacy
NFR-S1: TLS for all traffic; encryption at rest for database and stored media.
NFR-S2: RBAC enforced server-side; least-privilege roles (supports FR-6.1).
NFR-S3: Chat/brain uses a read-only DB role; no AI-initiated writes (supports FR-4.4).
NFR-S4: Worker video retained on-premises where feasible; configurable retention period.
NFR-S5: Full audit logging of confirms, edits, admin actions, and chat queries.
5.4 Usability
NFR-U1: A worker can complete a capture in ≤ 3 taps.
NFR-U2: Multilingual UI (English/Hindi/Gujarati); icon-led for low-literacy users.
NFR-U3: Touch-friendly, high-contrast UI suitable for factory-floor conditions.
5.5 Maintainability & Portability
NFR-M1: AI services modular and independently deployable.
NFR-M2: Vision provider abstracted behind one interface (supports FR-3.7).
NFR-M3: PWA runs on any modern browser; no app-store dependency.
5.6 Scalability
NFR-Sc1: Capture volume scalable to ~2× (≈800/day) without architectural change.
NFR-Sc2: Additional cameras addable by adding/upgrading edge capacity.

7.2 Acceptance Criteria (representative)
AC-1: Given a clear printed challan, capture extracts lot, quality, and meters correctly and commits without manual typing (FR-1.1–1.2).
AC-2: Given a low-confidence reading, the system holds it for confirm rather than committing wrong data (FR-3.1–3.3).
AC-3: At folding, shortage equals meters_in minus meters_out with no manual calculation (FR-2.3).
AC-4: At day end, a report is produced automatically with no human assembly (FR-4.1).
AC-5: A plain-language question returns an answer backed by a real query and shows the numbers (FR-4.3–4.5).
AC-6: A worker is flagged only when both low activity and low output coincide (FR-5.5).
AC-7: A worker cannot access another section’s data; a supervisor cannot perform admin actions (FR-6.1).
