1. Scope & Engineering Assumptions
This document translates the approved high-level design into a buildable specification with costs. It assumes the three core capabilities: photo-based capture (stock + job-card folding), the AI brain (auto-reports + chat over firm history), and camera-based worker efficiency monitoring.

2. System Architecture
Three input channels feed one central backend and database. AI services are isolated as independent modules so each can scale, fail, or be swapped without touching the others.
2.1 Layered view

2.2 Why this shape
Database is the single source of truth — the LLM never ‘remembers’ figures; it queries Postgres so every answer is auditable.
AI services are stateless workers behind a queue — capture spikes (e.g. dispatch rush) are absorbed without dropping data.
Vision is abstracted behind one interface — today it calls Claude; a hybrid OCR-first router can be inserted later purely as a config/strategy change.

4. Module A — Photo-Based Capture
4.1 Flow
Worker photographs challan / lot tag / folded-meter display in the PWA.
Image uploaded to object storage; a capture job is queued.
Vision service sends image + structured prompt to Claude Sonnet 4.6, requesting strict JSON (lot, quality, meters, doc type).
Service validates JSON, attaches a confidence score.
High confidence → auto-commits to ledger / job card. Low confidence → flagged for one-tap supervisor confirm.
4.2 Why Sonnet 4.6
Strong document-vision and structured-output reliability at $3 / $15 per million tokens (input/output). Haiku 4.5 ($1/$5) is used as a cheap pre-classifier to reject blurry/irrelevant photos before they reach Sonnet, cutting cost. Architecture stays hybrid-ready: a self-hosted OCR model can later handle clean printed challans, reserving the LLM for hard/handwritten cases.
4.3 Per-photo cost basis
A photo ≈ 1,200–1,600 image tokens + ~400 prompt tokens input; ~150 output tokens. Budget ~2,000 input + 150 output tokens per capture. Worked cost is in Section 7.
5. Module B — The Brain (Reports + Chat)
5.1 Daily report (automated)
A nightly scheduled job aggregates the day’s ledger, shortages, stock balance, and efficiency, then asks the LLM to write a plain-language summary. Delivered to dashboard + optional WhatsApp/email. No human assembles it.
5.2 Chat assistant (text-to-SQL + retrieval)
Owner asks a question in plain language (English/Hindi/Gujarati).
Brain translates it to a safe, read-only SQL query against Postgres (SELECT-only role, no writes).
Query runs; results returned to the LLM, which phrases the answer and shows the underlying numbers.
Long-horizon ‘why/history’ questions also pull relevant past records via pgvector retrieval.
Trust controls: read-only DB role, query whitelisting/validation, row limits, and full chat_audit logging of every question, the SQL it ran, and the answer.
5.3 Cost basis
Chat: ~3,000 input (schema + question + rows) + ~400 output tokens per turn. Daily report: ~8,000 input + ~1,200 output once per day. Prompt caching on the fixed schema cuts repeated input ~90%.
6. Module C — Camera-Based Worker Monitoring
The hardest and most sensitive module. Technically a continuous video-analytics pipeline; the efficiency signal is only trusted when fused with real job-card output.
6.1 Pipeline
Person detection & tracking — a YOLO-class model per camera stream identifies and tracks workers at each station.
Activity / idle classification — lightweight classifier estimates active vs idle time per worker per station.
Output fusion — camera activity is joined with meters completed (job cards). A worker is flagged only when low activity AND low output coincide — this avoids punishing fabric inspection or legitimate pauses.
Aggregation — written to cctv_activity and rolled into efficiency_daily for the report and flags.
Policy gate (must be agreed): the flag is a coaching/planning signal, not an automatic pay action. Define what is flagged, to whom, and retention period before go-live — labour-law and morale exposure otherwise.
6.2 Hardware/compute is the real cost driver
18 continuous video streams need sustained GPU inference. This is fundamentally different from the bursty, per-photo LLM calls, and is why Section 8 compares edge vs cloud explicitly.

8. CCTV Compute — Edge vs Cloud
18 continuous streams of person-detection + activity classification. Two ways to run it; this is the single biggest cost decision in the project.
8.1 Option A — On-site edge box (recommended)
One or two NVIDIA Jetson Orin-class devices on the factory LAN run YOLO + activity models locally via DeepStream (multi-stream on one device). Video never leaves the premises — better privacy, no bandwidth cost, resilient to internet outages.

8.3 Verdict
Edge wins for this use case. Cloud’s recurring $420–$870/mo overtakes the edge hardware’s one-time cost within ~6–10 months, and keeps charging forever. Edge also keeps worker video on-premises (privacy + labour-relations) and survives internet outages — important on a factory floor. Recommend edge unless the client wants zero upfront capex.

12. Recommended Delivery Phases
Phase 1 (wk 1–10): DB + vision capture + dashboards + daily report. Delivers ‘no manual entry’ immediately. Recurring cost in this phase ~$110–150/mo, zero CCTV capex.
Phase 2 (wk 8–12): Brain chat assistant over the now-accumulating history.
Phase 3 (wk 12–20): CCTV monitoring + edge deploy + output fusion. Triggers the hardware capex — deferred until output data exists to validate flags.
